# PROMPTS — AI エージェントへの指示のサンプル

このテンプレートから作ったアドオンを、AI エージェント（Claude Code、Codex など）と開発するときの、指示（プロンプト）のサンプル集です。`[ ]` の中を書き換えて使います。手で直すことが多いため、日本語で書きます（`docs/knowledge/`・`docs/adr/` と同じ）。

エージェントは、指示がなくても `AGENTS.md` のワークフロー（読む → 計画 → 実装 → 記録 → 検証 → 決定とナレッジの記録 → 報告）に従います。そのため、プロンプトに書くのは「**何を作りたいか**」「**やらないこと**」「**どこで確認するか**」で足ります。規則（UUID、名前空間、実験的機能なし、Marketplace のフォルダ構成など）を、プロンプトで繰り返す必要はありません。

## 前提: 開発と確認の環境

| 環境 | 役割 | 誰が操作するか |
| --- | --- | --- |
| macOS | 開発（`pnpm validate` / `build` / `test` / `package`）。Mac 用の統合版はないので、ゲームは動かない | エージェント |
| Windows 11 VM（VMPal） | ゲーム内の確認。`dist/<slug>_BP`・`_RP` を開発用フォルダにコピーして確認する（`docs/knowledge/device-testing-windows-vm/`） | エージェント（VMPal の MCP 経由）または人 |
| iPhone / iPad | 実機での確認。`pnpm package` の `.mcaddon` を Finder から AirDrop する（`docs/knowledge/device-testing-ios/`） | 人 |

- iPhone に入れるビルドは、毎回パッチ番号を上げる（UUID とバージョンが同じパックは、取り込まれない。`docs/adr/0002-versioning.md`）。
- 2 人での確認は、VM をホストにして、iPhone が LAN で参加する（VM のネットワークを `bridged` にする）。

## どのプロンプトにも足せる定型句

必要なものだけを、プロンプトの最後に貼ります。

```
- まず計画（変更するファイル、追加する識別子、触る ADR とナレッジ）を見せてください。私が OK するまで実装しないでください。
- 確認は Windows の VM で行ってください。ビルドを VM に入れて、TESTING.md のケースを実行し、スクリーンショットで結果を見せてください。
- 確認は私が iPhone で行います。パッチ番号を上げて pnpm package し、.mcaddon のパスと、確認してほしいケースの一覧を教えてください。
- 決めたことは docs/adr/ に、分かったこと（公式資料と違う動作など）は docs/knowledge/ に残してください。
- コミットまでしてください（push はしないでください）。/ コミットはしないでください。
```

## 0. 初期設定（テンプレートからリポジトリを作った直後に 1 回）

```
このテンプレートから、新しいアドオンを作ります。初期設定をしてください。

- 名前: [Smooth Glass]（日本語: [滑らかなガラス]）
- slug: [smooth-glass]（リポジトリ名は mc-addon-[smooth-glass]）
- 名前空間: [to3izo_sg]（<作者名>_<パック略称>）
- 説明（英語）: [Adds smooth variants of every glass block and pane.]
- 説明（日本語）: [すべてのガラスと板ガラスに、つなげると枠が消える「滑らかな」版を追加する。]
- 作者: [to3izo]
- 対応バージョン: addon.config.json の minEngineVersion のままでよい

手順:
1. テンプレート（mc-addon-template）の docs/ADDONS.md を見て、名前空間・slug・名前・機能が、既存のアドオンと衝突・重複しないかを確認する。
   重複しそうなら、実装に入る前に教えてください。
2. addon.config.json を更新し（descriptionJa も入れる）、pnpm init:addon を実行する。
3. docs/adr/0001・0002 の「日付」を今日に書き換え、このアドオンでも採用でよいかを確認する。
4. pnpm validate && pnpm build && pnpm test が通ることを確認する。
5. テンプレート側の docs/ADDONS.md に追加する 1 行を、文章で示してください（このリポジトリでは編集しない）。
```

## 1. アイデアから仕様と計画を作る（実装はまだ）

いきなり実装させず、**仕様（`docs/SPEC.md`）と計画を先に確認する**のが、作り直しを減らす一番のコツです。

```
次のアイデアで、アドオンを作りたいです。まだ実装しないでください。
docs/SPEC.md を埋めて、実装の計画を見せてください。

## アイデア
[ワールドの全プレイヤーで中身を共有する、新しいエンダーチェストを追加したい]

## 遊ぶ人
[友達とマルチで遊ぶサバイバルのプレイヤー]

## バニラとの関係
[見た目・硬さ・開閉音は、バニラのエンダーチェストに近づける（数値は調べてから決める）]

## やらないこと
- [バニラのエンダーチェストの動作は変えない]
- [〇〇の機能は作らない]

## 計画に入れてほしいこと
- 追加するブロック・アイテム・エンティティ・レシピと、識別子（<名前空間>:<名前>）の一覧
- 実験的機能なしで実現できるか。できない部分があれば、代わりの方法か、諦める範囲
- バニラの値の出どころ（bedrock-samples、Minecraft Wiki、Bedrock Wiki）
- 読んだ docs/knowledge/ のテーマと、関係する落とし穴
- ゲーム内で確認するケース（TESTING.md に足すもの）
- ADR に残すべき決定
```

計画を確認して、問題がなければ続けて送ります。

```
計画どおりに実装してください。[〇〇は △△ に変えてください。]
AGENTS.md の Definition of Done をすべて満たし、CONTENT.md・TESTING.md（英・日）・CHANGELOG.md、
必要な ADR とナレッジも更新してください。最後に、変更点と、まだゲーム内で確認していないことを報告してください。
```

## 2. ブロックを追加する

ブロックは、カリング・モデル・テクスチャ・パーミュテーションの落とし穴が多いので、関係するナレッジを読ませます。

```
ブロックを追加してください。

- 表示名: [滑らかな遮光ガラス板] / 英語: [Smooth Tinted Glass Pane]
- 識別子: [<名前空間>:smooth_tinted_glass_pane]
- 見た目: [バニラの遮光ガラス板と同じ形。同じ種類をつなげると、間の枠線が消える]
- バニラに合わせる値: [硬さ・爆発耐性・光の透過・音]（値は調べてから使ってください）
- 入手方法: [石切台で、バニラの遮光ガラス板と相互に交換]
- ドロップ: [シルクタッチのときだけ、自分をドロップ]
- クリエイティブのタブ・グループ: [バニラの板ガラスの近く]

docs/knowledge/ の block-definitions・block-culling・block-geometry・block-textures-and-icons を先に読んでください。
状態（states）を使う場合は、パーミュテーションの合計（1 万未満）も計算して報告してください。
確認は、空中と、不透明なブロックの隣の両方で、バニラと並べて行うケースにしてください。
```

## 3. アイテムとレシピを追加する

```
アイテムを追加してください。

- 表示名: [霊火の欠片] / 英語: [Spirit Flame Shard]
- 識別子: [<名前空間>:spirit_flame_shard]
- 見た目: [青白く光る小さな結晶。テクスチャは仮でよい（あとで assets/ から差し替える）]
- スタック数: [64]
- 入手方法: [〇〇のドロップ / 作業台で △△ から作る]
- 用途: [〇〇の材料]

レシピには、このアドオンのアイテムを入れてください（バニラのアイテムだけの形は、ほかのアドオンと衝突するため）。
```

## 4. エンティティを追加する

```
エンティティを追加してください。

- 表示名: [ランタンゴースト] / 英語: [Lantern Ghost]
- 識別子: [<名前空間>:lantern_ghost]
- 動き: [夜だけ、村の近くに出る。プレイヤーに近づいて攻撃する。昼になると消える]
- 体力・攻撃力・速さ: [ゾンビくらい]（バニラの値を調べて、近い値にしてください）
- ドロップ: [霊火の欠片を 0〜1 個]
- モデル: [仮の箱でよい。あとで assets/ の .bbmodel から差し替える]

iPhone ではタップが「攻撃」になるので、右クリック（使う）を前提にした操作がある場合は、計画の段階で教えてください
（docs/knowledge/device-testing-ios/）。
```

## 5. スクリプトで仕組みを作る

```
スクリプトの機能を追加してください。scripts/features/[spirit_lantern]/ に分けて作ってください。

## やりたいこと
[霊火ランタンを手に持っている間、周囲 8 ブロックの敵に、発光のエフェクトを付ける]

## 条件
- 毎 tick の処理はしない（[1 秒に 1 回] 程度でよい）
- マルチプレイで、全員に正しく動くこと
- ベータ版の API は使わない（使わないとできない場合は、実装する前に教えてください）
- 計算だけの部分（範囲の判定など）は、ユニットテストを書く
```

## 6. 自分で作った素材を組み込む

```
assets/ に素材を置きました。リソースパックに組み込んでください。

- assets/blockbench/[lantern_ghost.bbmodel] → エンティティのモデルとアニメーション
- assets/textures/[lantern_ghost.png] → そのテクスチャ
- assets/audio/[ghost_idle.wav] → 待機中の音（.ogg のモノラルに変換）

原本は assets/ に残し、ゲームが読むファイルだけを、resource_pack/ の <作者名>/<パック名>/ の下に入れてください。
仮の素材から差し替える場合は、使われなくなったファイルを消してください。
```

## 7. Windows の VM で確認する（エージェントに操作させる）

```
いまのビルドを、Windows の VM で確認してください。

1. pnpm build して、dist/<slug>_BP と _RP を、VM の開発用フォルダにコピーする
2. [新規のフラット・クリエイティブ / 既存の「テスト用」] ワールドで、ビヘイビアパックを有効にする
3. docs/TESTING.md の [スモークテストと F-xx-01〜05] を実行する
4. 各ケースの結果（合否）と、スクリーンショット、コンテンツログのエラーを報告する

操作の落とし穴は docs/knowledge/device-testing-windows-vm/ にあります（JIS 配列のキー入力、チャットの閉じ方など）。
新しく分かった落とし穴は、同じナレッジに追記してください。
```

## 8. iPhone / iPad で確認する（人が操作する）

ビルドを作らせるとき:

```
iPhone で確認するので、確認用のビルドを作ってください。
パッチ番号を上げて（pnpm version:set）、pnpm package を実行し、
.mcaddon のパスと、確認してほしいケース（TESTING.md の ID と手順）を短くまとめてください。
```

結果を伝えるとき（記録まで任せられます）:

```
iPhone（iOS [26.x]、Minecraft [1.26.50]）で確認しました。TESTING.md と、必要なら knowledge に記録してください。

- [F-xx-01]: OK
- [F-xx-02]: NG。[板ガラスをつなげても、上下の枠線が残る]（スクリーンショットを添付）
- 気づいたこと: [新規ワールドの初回だけ「読み込みに失敗しました」と出た]
```

## 9. 不具合を直す

「**何をしたら**」「**どうなるはずが**」「**どうなったか**」の 3 つと、コンテンツログの全文があると、原因を特定しやすくなります。

```
ゲーム内で不具合がありました。原因を調べて、直してください。

- 環境: [iPhone / Windows の VM]、Minecraft [1.26.50]、[シングル / 2 人]、ビルド [0.1.4]
- 手順: [チェストを置く → ワールドを抜けて入り直す → チェストを開く]
- 期待: [中身が残っている]
- 実際: [中身が空になっている]
- コンテンツログ: [エラー文の全文を貼る]

原因が分かったら、直す前に、原因と直し方を説明してください。
直したら、再発を確かめるケースを TESTING.md に足し、knowledge に残す価値があれば追記してください。
```

## 10. 数値を調整する

```
バランスを調整したいです。仕組みやファイルの構成は変えずに、数値だけ変えてください。

- [ランタンゴーストの出現率]: [今の半分くらい]
- [体力]: [20 → 14]
- [霊火の欠片のドロップ]: [1〜2 個 → 0〜1 個]

変更前と変更後を表で見せてください。仕様が変わるので、マイナー番号を上げる対象かどうかも教えてください（ADR-0002）。
```

## 11. 調べるだけ（実装しない）

```
実装はしないでください。調べた結果だけを教えてください。

[ブロックにインベントリ（コンテナ）を持たせること] は、対応バージョン（minEngineVersion）で、
実験的機能なしに実現できますか？
- できる場合: 方法と、必要なコンポーネント・API、出どころ
- できない場合: 代わりの方法と、その制約
Bedrock Wiki の履歴、bedrock-samples（版を確認してから）、ベータ版ではない Script API の型定義で、確認してください。
分かったことは docs/knowledge/ に残してください。
```

## 12. 決定とナレッジを残す

作業の途中で決めたことや、分かったことを、あとから残してもらうとき:

```
この会話で決めたことを、ADR に残してください。

- 決定: [〇〇は、実験的機能なしでは実現できないので、△△ で代わりにする]
- 採らなかった案: [□□（理由: ……）]
- 受け入れた制約: [強制終了すると、アイテムが消えることがある]

制約は、README・CHANGELOG の既知の問題・SPEC の制約にも、同じ内容で書いてください。
```

```
今回分かったことを、docs/knowledge/ に残してください。
どうやって分かったか（実機で確認済み・公式資料・推測）と、機種とバージョンを書いてください。

- [setblock で置いたカスタムブロックは、向きが placement_direction の既定になる]
```

## 13. リリースの準備

```
v[0.2.0] のリリースの準備をしてください。

1. README（英・日）を、テンプレートの説明から、利用者向けのアドオンの説明に書き換える
   （一言の説明、特徴、レシピ、使い方、バニラとの違い、注意事項、確認した範囲と未確認の範囲、インストール方法）。
   確認したことだけを書き、「安全」「バニラと同じ」などの断定は避けてください。
2. pnpm version:set [0.2.0]、CHANGELOG の Unreleased を [0.2.0] に移す（確認用ビルドの変更はまとめて書く）
3. pnpm validate && pnpm build && pnpm test && pnpm package
4. TESTING.md のリリース前チェックリストのうち、未実施の項目を教えてください

タグの作成と push は私が行うので、しないでください。
```

## 14. 紹介用のスクリーンショットと記事

スクリーンショット（VM で撮る）:

```
紹介用のスクリーンショットを、Windows の VM で撮ってください。

- 場面: [昼の平原に、色付きの滑らかなガラスを並べた家 / 夜の暗い部屋で光るランタン]
- HUD は消す（F1）。画面全体を元の解像度で保存する
- 元の画像は media/source/screenshots/、切り抜いた版は media/exports/ に置く

撮り方の手順と落とし穴は、docs/knowledge/release-and-media/ にあります。
```

紹介記事（別の AI やライターに渡すプロンプトを作らせる）:

```
このアドオンの紹介記事を、別の AI に書いてもらうためのプロンプトを作ってください。

- 事実の一覧は、README・CHANGELOG・TESTING.md の確認済みのものだけにする
- 注意事項（データが失われるリスクなど）は必ず書かせる
- 書いてはいけない表現（未確認の断定、公式を思わせる表現）と、未確認の機種は「未確認」と書くことを明記する
- 出力は Markdown。末尾に「確認が必要な点」を付けさせる
```

## 15. Marketplace の要件を満たしているか点検する

```
Marketplace の協調型アドオンの要件を満たしているか、点検してください。直す前に、結果の一覧を見せてください。

- バニラの上書き・変更がないか（ブロック、アイテム、レシピ、テクスチャ、音、.lang）
- 実験的機能を使っていないか
- 名前空間と、<作者名>/<パック名>/ のフォルダ構成
- サイズ（25 MB・3,500 ファイル未満）、パーミュテーションの合計（1 万未満）、テクスチャの大きさ（256×256 以下）
- Mojang のテクスチャのコピーや色替えがないか

基準は AGENTS.md の Marketplace policy と、docs/knowledge/marketplace/ です。
```

## うまく伝えるコツ

- **1 回の依頼で 1 つのテーマにする。** 「ブロックの追加」と「別の不具合の修正」は、分けて頼むと確認しやすくなります（`AGENTS.md` の Git policy と同じ考え方）。
- **大きな変更は、計画を先に見せてもらう。** 実験的機能が必要と分かって作り直す、といった手戻りを減らせます。
- **「やらないこと」を書く。** 書かないと、気を利かせて、頼んでいない機能まで作ることがあります。
- **バニラの値は「調べてから」と頼む。** 記憶で書いた古い挙動が入るのを防げます（`docs/knowledge/vanilla-reference/`）。
- **ゲーム内の結果を返す。** エージェントは iPhone を操作できません。結果を伝えれば、TESTING.md やナレッジへの記録まで任せられます。
- **決めたことは、その場で ADR に残してもらう。** 会話が終わると、理由は残りません。
