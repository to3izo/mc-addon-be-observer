# ADR-0013: バージョンを、セマンティック バージョニングに沿って付ける

- 状態: 採用（ADR-0002 を置き換える）
- 日付: 2026-10-18
- 決定者: 運営（利用者の指示: 一般的なセマンティック バージョニングをもとに、推奨する方式で決めてよい）

## 背景
ADR-0002 は、テンプレートの出発点の方針を、このアドオンに合わせて直したものだった。iPhone への確認用ビルドごとにパッチを上げる、「1.0.0 = Marketplace 公開」を読み替える、など、いまは当てはまらない前提が残っていた。1.0.0 を公開し、このアドオンは Marketplace に出さず、BDS だけを対象にする（ADR-0006）。外部ツールの作者が、番号を見て更新の影響を判断できるように、方針を定め直す。

## 決定

### 基本
- [Semantic Versioning 2.0.0](https://semver.org/) に従う。番号は `MAJOR.MINOR.PATCH` の 3 つの数だけ。
- アドオン全体で 1 つの番号を使う（`package.json`、両パックのマニフェスト、モジュール、BP と RP の依存）。変えるのは `pnpm version:set` だけで、同じ変更で `scripts/shared/constants/version.ts` の `ADDON_VERSION` も直す（テストが一致を確かめる。`AGENTS.md` の Version policy）。
- タグは `v<MAJOR.MINOR.PATCH>`。公開したタグとリリースは、動かさない・作り直さない。誤りは、次のパッチで直す。
- すべてのリリースに、`CHANGELOG.md` の節を付ける（Keep a Changelog。`Added`・`Changed`・`Deprecated`・`Removed`・`Fixed`・`Security`）。

### 公開の API（番号が守る範囲）
1. プロトコル（`docs/PROTOCOL.md`）: 要求・応答・通知の行の形、接頭辞、メソッド、引数、項目、型・単位・意味、エラーのコード、上限値の既定。
2. 入口: `/scriptevent to3izo_bo:query` と、カスタムコマンド `/to3izo_bo:query`、その権限（ADR-0010）。
3. 対応環境: BDS（ADR-0006）と、導入の手順。
4. ワールドに残るもの: 名前空間 `to3izo_bo` の識別子（いまは読み取り専用で、ワールドに書くものはない）。

### どの番号を上げるか
| 上げる番号 | 変更 | 例 |
| --- | --- | --- |
| MAJOR | 公開の API の、互換でない変更 | `protocol` の番号を上げる。メソッド・項目・エラーのコード・通知の種類・入口を消す・名前を変える。項目の型・単位・意味を変える。前は受け付けた要求を拒否する（上限値を下げる、権限を厳しくする）。対応する OS などを減らす。ワールドとの互換を壊す |
| MINOR | 互換な追加と、仕様の変更 | メソッド・節・任意の引数・応答の項目・通知の種類・エラーのコードを足す。非推奨にする。上限値を上げる。新しい Bedrock の版に合わせて、`min_engine_version` や `@minecraft/server` の版を上げる |
| PATCH | 公開の API を変えない変更 | `docs/PROTOCOL.md` のとおりに動くようにする不具合の修正。性能、文書、テスト、ビルドの道具 |

- 1 つのリリースに複数の変更があるときは、いちばん大きいものに合わせる。番号を上げたら、下の桁を 0 に戻す。
- `protocol`（整数）は、プロトコルが互換でなくなるときだけ上げる（`docs/PROTOCOL.md` §8）。`protocol` を上げるリリースは、必ず MAJOR を上げる。古い `protocol` を `capabilities.protocol.supported` に残して並行して扱うことはできるが、そこから外すのは MAJOR。

### 非推奨と削除
- 消したいものは、まず MINOR で非推奨にする（`CHANGELOG.md` の `Deprecated` と、`docs/PROTOCOL.md` に書く）。動きは変えない。
- 消すのは、次の MAJOR から。非推奨にしたリリースと、消すリリースの間に、少なくとも 1 つのリリースを置く。

### 試験版
- プレリリースの番号（`-beta.1`・`-rc.1` など）は使わない。マニフェストの版は 3 つの数で、プレリリースを表せない。
- ゲーム内の確認は、作業ツリーから作ったローカルビルドで、番号を上げずに行う（`pnpm build` のパックを開発用のフォルダに入れる。`pnpm deploy` か手でコピーする。開発用のフォルダのパックは、同じ番号でも上書きされる）。番号を付けるのは、公開するリリースだけ。

### サポート
- 修正するのは、最新の MAJOR の、最新のリリースだけ（`SECURITY.md`）。古い MAJOR には、修正を戻さない。

## 理由・検討した案
| 案 | 判断 | 理由 |
| --- | --- | --- |
| SemVer に、公開の API の範囲と例を足して使う | **採る** | 外部ツールの作者に、いちばん知られている決まり。範囲と例を書くと、境目の判断がぶれない |
| ADR-0002 のまま | 採らない | iPhone と Marketplace の前提が残り、非推奨・試験版・サポートの決まりがない |
| 番号を Bedrock の版に合わせる（例: 1.26.52） | 採らない | アドオンの変更とゲームの更新が混ざり、ツールへの影響が番号から読めない |
| 日付の番号（CalVer） | 採らない | 互換でない変更が番号から分からない |
| `min_engine_version` を上げたら MAJOR | 採らない | Bedrock は、クライアントとサーバーの版が合わないとつながらず、BDS の運用者は結局ゲームの更新に合わせる。毎回 MAJOR にすると、プロトコルが壊れたときと区別できない。前のリリースは、古い BDS で使い続けられる |
| 試験版にプレリリースの番号を付ける | 採らない | マニフェストで表せない。ローカルビルドで足りる |

## 影響
- `AGENTS.md` の Version policy を、この ADR の要約に書き換えた。
- `docs/PROTOCOL.md` §8 の参照先を、この ADR にした。
- `SECURITY.md` の Supported versions を、「最新の MAJOR の最新のリリース」にした。
- ADR-0002 は、置き換え済み。1.0.0 の意味（外部の人が使える最初の公開版）は、すでに満たしたので、引き継がない。

## 経過
- 2026-10-18: 利用者の指示で、SemVer をもとに方針を定めた。次の版から適用する（1.0.0 は ADR-0002 の方針で付けたが、この ADR とも矛盾しない）。
