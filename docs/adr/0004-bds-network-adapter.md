# ADR-0004: BDS 専用の通信アダプター（server-net）は作らない

- 状態: 却下（2026-10-18。Phase 3 を閉じた）
- 日付: 2026-10-18（提案）、2026-10-18（却下）
- 決定者: 運営（利用者の判断）

## 背景
外部ツール（例: Mac 上で動くツール）が、Windows VM の BDS から観測をネットワーク経由で受け取れると便利になる。そのための `@minecraft/server-net` は、次の性質を持つ（`docs/RESEARCH.md` §2.4・§2.5）。

- 公開版はすべてベータ（`1.0.0-beta.*`）。BDS でしか動かない。ワールドで **Beta APIs の実験**が必要。2026-10-18 の `npm view` でも、ベータでない版は 0 件だった（`latest` も `1.0.0-beta.*`）。
- 待ち受け（HTTP サーバー）の API はない。外向きの HTTP と WebSocket のクライアントだけ。
- manifest に「あれば使う」任意の依存を書く仕組みは記載がない。動的 `import()` や条件分岐で、依存の宣言の問題を避けられる根拠もない。
- テンプレートの道具（`tools/`）は「1 アドオン = BP と RP が 1 つずつ」を前提にし、ほかのパックへの依存をエラーにする。

一方、Phase 1・2 では、標準出力での回収が成り立った。`content-log-console-output-enabled=true` で、応答と出来事の行が遅れなく BDS の標準出力に出る（3,965 文字の行も欠けない）。13 のメソッドと出来事の通知を、BDS 1.26.52.3 で確認した（`docs/knowledge/bds-local-server/` §8、`docs/TESTING.md`）。

## 決定
1. **Phase 3 の通信アダプター（server-net で BDS から送る別のアドオン）は作らない。** Phase 3 は閉じる。
2. **観測コア（このリポジトリの BP）は、`@minecraft/server` 以外に依存しない。** server-net・server-admin を manifest にも `scripts/` にも入れない（`pnpm validate` が、宣言と import の一致を検査する）。
3. 入出力は、`/scriptevent`・operator のカスタムコマンドと、1 行 JSON のログだけにする（ADR-0003・ADR-0010）。コアへの `"reply": "event"`（`to3izo_bo:response` の script event）は**足さない**。
4. 観測を BDS のホストの外（Mac など）へ届けるのは、**外部ツールの責務**とする（`docs/PROTOCOL.md` §9）。ネットワークを使う場合も、Minecraft の外（参考のブリッジのような、BDS の標準入出力をつなぐ普通のプログラム）で行い、ベータ版の API は使わない。その場合も、下の「受信側の条件」と `SECURITY.md` の規則に従う。

## 理由・検討した案

### 比べたもの
| | 標準出力＋ブリッジ（採る） | server-net のアダプター（却下） |
| --- | --- | --- |
| 要求の経路 | BDS の標準入力、operator のチャット | 同じ（受信口から命令を送る経路は作らない、という条件だったため） |
| 応答・出来事の経路 | 標準出力 → ブリッジ → 外部ツール | BDS から外へ HTTP で送る |
| 実験的機能 | 不要 | ワールドで Beta APIs が必要（後からオフにできない） |
| 実機での確認 | 13 メソッドと出来事の通知を確認済み | 未確認（上限値・許可リスト・`force_tls` の設定場所も不明） |

### 却下した理由
1. **残っている課題は、Minecraft の外の問題だった。** 応答は標準出力に遅れなく出る。課題は「BDS のホストから Mac へ行を届ける」ことだけで、ブリッジの側でベータ版なしに解ける。
2. **AI がプレイするワールドそのものを、実験的機能つきにすることになる。** 当初は、例外を「検証用のワールドだけ」に限る案だった。しかし、使うためには、遊ぶワールドで Beta APIs を有効にしなければならない。実績は解除されず、後からオフにもできない。ADR-0001 の例外として、重すぎる。
3. **ブリッジはなくならない。** 要求は標準入力から送るので、ブリッジとアダプターの両方を保守することになる。利点（外部ツールが読みに行かずに、観測が届く）に比べて、部品と確認の手間が倍になる。
4. **ベータ版は、ゲームのバージョンに縛られる**（`1.0.0-beta.1.26.52-stable` など）。BDS を更新するたびに直す必要があり、API が変わったり、なくなったりもしうる。初回リリースの前に、壊れやすい部品を抱えることになる。
5. Mac 側に、ネットワークからの受信口が増える。必要なら、ブリッジの側でも同じ条件で作れるので、アダプターの理由にならない。

### 検討した案（2026-10-18 の提案の時点）
| 案 | 判断 | 理由 |
| --- | --- | --- |
| コアの BP に server-net を足す | 採らない | ベータで ADR-0001 に反する。コアの対応範囲が壊れる |
| 動的 `import()` や環境の判定で、使えるときだけ使う | 採らない | manifest に宣言しないモジュールは読み込めない。宣言すれば非対応の環境で問題になる。避けられるという根拠がない |
| 同じリポジトリで 2 つ目の BP を作る（ビルドの派生） | 採らない | `tools/` の build・validate・package を作り替える必要があり、「1 アドオン = 1 リポジトリ」とも合わない |
| BDS の `system_behavior_packs` にアダプターを置く | 採らない | ワールドに入れずに済む可能性はあったが、ベータのモジュールと実験の扱いは未確認。どちらにしても、ベータ版を使う理由（上）が残る |
| 別リポジトリの別アドオンで、script event だけでつなぐ | 却下（2026-10-18） | 分け方としては最もよかったが、上の「却下した理由」による |
| ネットワークを使わず、BDS の標準出力を外部ツールが回収する | **採る** | 実験的機能もトークンも要らない。Phase 1・2 で実際に動いた |

### 見直す条件
次のどれかが起きたら、新しい ADR で決め直す（この ADR は消さない）。
- `@minecraft/server-net`（と `server-admin`）に、実験的機能が要らない安定版が出た。
- ベータ版でしか取れない観測（チャットの `chatSend` など）が、どうしても必要になった（ADR-0008 の「チャットを扱わなかった」）。
- 標準出力での回収では、外部ツールの要件（遅れ・量）を満たせないと、実測で分かった。

## 受信側の条件（観測をネットワークで受け取る場合）
ブリッジなど Minecraft の外の部品が、観測の行を Mac へ送る場合にも、受信側（外部ツール）はこれに従う。もとは Phase 3 の受信口の条件（当時の `docs/PLAN.md` の提案 B・C）だった。以下は提案で、受信側の設計に合わせて取捨する。

1. 既存の汎用ローカル API は、loopback（127.0.0.1）のままにする。VM 用の受信口は、別のリスナーとして足す。
2. bind するのは、VMPal のネットワーク側の Mac のアドレス（<VMPal のローカルネットワーク> のブリッジ）だけにする。`0.0.0.0` にすると、自宅の Wi-Fi にも出てしまう。
3. 接続元は、VM のアドレス（例: <VM のローカル側のアドレス>）だけを受け付ける。ただし、アドレスは偽装できるので、これだけを頼りにしない。
4. 認証: 推測困難な共有トークン（例: 32 バイト以上の乱数）を `Authorization` ヘッダーで受け、定数時間で比較する。置き場所は、Mac 側では OS のキーチェーンなど、VM 側では OS の秘密の置き場所。Git・パック・ワールド・スクリプトの定数・ログには置かない。トークンを替える手順も用意する。
5. 受け付けるのは観測の行（`to3izo_bo.response`・`to3izo_bo.event`）だけにし、それ以外は拒否する。受信口から Minecraft へ命令を送る経路は作らない。
6. 制限: 1 メッセージの最大サイズ（例: 16 KiB）、頻度（例: 毎秒 10 回を超えたら捨てる）、同時接続は 1 本。超えたら拒否し、ログには回数だけ残す。送る側も、キューに上限を付け、再接続は待ち時間（指数バックオフ）を置いてから行う。
7. ログに、トークンやヘッダーの値を出さない。残すのは、拒否の理由と回数だけ。
8. 受信時刻を記録し、`tick`・`time` と並べて保存する。VM と Mac の時計が同期していると仮定しない。
9. 暗号化: 平文の http/ws を使うなら、同じネットワークの上で読まれうることを文書に書く。「内部ネットワークだから安全」とは説明しない。
10. 状態を確認する口（health）を作るなら、それにも認証を掛ける。既存の OSS（chapmanjw の MCP サーバー）は認証なしだった。

VM から Mac に届くかの確かめ方は `docs/knowledge/bds-local-server/` §7。

## 影響
- `docs/ROADMAP.md`: Phase 3 を閉じ、次の段階を初回リリースにした。VM から Mac へ届ける作業は「運用・外部」の項目にした。
- `docs/SPEC.md`・`docs/ARCHITECTURE.md`・`SECURITY.md`: 通信アダプターを「作らない」と書き、`to3izo_bo:response` を公開の識別子の予定から外した。
- `docs/TESTING.md`: OBS-ENV-07 を「対象外」にした。
- ADR-0001 の例外は生じない（このリポジトリにも、関連するリポジトリにも、ベータ版の API を使う部品はない）。

## 経過
- 2026-10-18: 調査の結果を受けて提案。別リポジトリに分ける案と、採否を Phase 2 の後に決める進め方が承認された（状態は保留のまま）。
- 2026-10-18: 対象を BDS だけにした（ADR-0006）。「通常ワールドで動かなくなる」は分ける理由でなくなったが、「ベータ版で、ワールドに実験的機能が必要」は残る。BDS の標準出力での回収が Phase 1 で動いた（`docs/knowledge/bds-local-server/` §8）ので、Phase 3 が必要かは Phase 2 のあとに改めて判断する。
- 2026-10-18: `docs/PLAN.md` を廃止した。そこにあった Phase 3 の規則と外部ツールへの提案（B・C）を、この ADR の「採用する場合の条件」に移した。
- 2026-10-18: Phase 2 が終わった。利用者の指示で、Phase 3 は別のセッションで扱う。採否もそこで決める（状態は保留のまま）。
- 2026-10-18: Phase 3 のセッションで、標準出力＋ブリッジと比べた。利点・費用・リスクを示し、利用者が**却下**に決めた（上の「却下した理由」）。送信側の条件（同時の要求は 1 件、`SecretString` でトークンを送る、など）は、server-net に固有なので外した。受信側の条件は、ネットワークで受け取る場合の条件として残した。server-net の上限値・許可リスト・`force_tls` の設定場所は、確かめないままにした（`docs/knowledge/bds-local-server/` §5）。
