# ADR-0004: BDS 専用の通信アダプターは、観測コアから切り離し、初版には入れない

- 状態: 保留（提案。Phase 2 の終わりに、採るかどうかを決める）
- 日付: 2026-10-18
- 決定者: 運営（承認待ち）

## 背景
外部ツール（Mac 上の Play Conductor）が、Windows VM の BDS から観測をネットワーク経由で受け取れると便利になる。そのための `@minecraft/server-net` は、次の性質を持つ（`docs/RESEARCH.md` §2.4・§2.5）。

- 公開版はすべてベータ（`1.0.0-beta.*`）。BDS でしか動かない。ワールドで **Beta APIs の実験**が必要。
- 待ち受け（HTTP サーバー）の API はない。外向きの HTTP と WebSocket のクライアントだけ。
- manifest に「あれば使う」任意の依存を書く仕組みは記載がない。動的 `import()` や条件分岐で、依存の宣言の問題を避けられる根拠もない。
- テンプレートの道具（`tools/`）は「1 アドオン = BP と RP が 1 つずつ」を前提にし、ほかのパックへの依存をエラーにする。

## 決定（提案）
1. **観測コア（このリポジトリの BP）は、`@minecraft/server` 以外に依存しない。** server-net・server-admin を manifest にも `scripts/` にも入れない（`pnpm validate` が、宣言と import の一致を検査する）。
2. **初版（Phase 1・2）には通信アダプターを入れない。** 入出力は `/scriptevent` と 1 行 JSON ログだけ（ADR-0003）。
3. 採る場合（Phase 3）は、**別のリポジトリの別のアドオン**（例: `mc-addon-be-observer-bds-link`、別の名前空間と UUID）として作る。アダプターはコアの JS を読み込まず、**script event だけでコアとやり取りする**:
   - アダプター → コア: `system.sendScriptEvent("to3izo_bo:query", <要求 JSON>)`
   - コア → アダプター: 要求に `"reply": "event"` があるときだけ、コアが応答を `system.sendScriptEvent("to3izo_bo:response", <応答 JSON>)` でも出す（Phase 3 で足す、読み取り専用のままの小さな追加。プロトコルの互換な追加）。
   - アダプター → 外部: server-net の外向き HTTP（または WebSocket）で、1 つの決まった送り先にだけ送る。
4. アダプターは ADR-0001 の例外になる（Beta APIs の実験が必要）。例外は、そのアドオンと、それを入れる **BDS の検証用ワールドだけ**に限る。通常の配布物（このリポジトリの `.mcaddon`）と、既存の検証ワールド `addon-lab-flat` には影響させない。

## 理由・検討した案
| 案 | 判断 | 理由 |
| --- | --- | --- |
| コアの BP に server-net を足す | 採らない | 通常ワールド・Realms で動かないモジュールへの依存になり、コアの対応範囲が壊れる。ベータで ADR-0001 に反する |
| 動的 `import()` や環境の判定で、使えるときだけ使う | 採らない | manifest に宣言しないモジュールは読み込めない。宣言すれば非対応の環境で問題になる。避けられるという根拠がない |
| 同じリポジトリで 2 つ目の BP を作る（ビルドの派生） | 採らない（今は） | `tools/` の build・validate・package を作り替える必要があり、テンプレート全体に影響する。「1 アドオン = 1 リポジトリ」とも合わない |
| BDS の `system_behavior_packs` にアダプターを置く | 検討の余地あり | BDS 同梱の文書では、全ワールドに適用する管理者用のパックの置き場所。ワールドに入れずに済む可能性があるが、ベータのモジュールと実験の扱いは未確認 |
| 別リポジトリの別アドオンで、script event だけでつなぐ | **提案** | コアは変わらず、両者の依存は文書化した script event の契約だけ。アダプターを入れない環境に影響しない |
| ネットワークを使わず、BDS の標準出力のログをファイルで Mac に渡す | Phase 2 で先に試す | 実験的機能もトークンも要らない。外部ツールの責務（ログの回収）として実現できるなら、Phase 3 自体が不要になる |

## 採用する場合の条件
Phase 3 を採るときは、次を満たす設計にする（当時の `docs/PLAN.md` から移した）。

### 送信側（アダプターのアドオン）
- 送り先は 1 つ、外向きだけ、観測のメッセージだけ。受信口から Minecraft へ命令を送る経路は作らない。
- 同時の要求は 1 件にする。`HttpRequestLimitExceededError` は同時実行数の上限で、値は記載がないため（`docs/RESEARCH.md` §2.4）。
- 送信待ちのキューには上限を付ける。古い観測は捨て、最新を優先する。
- 定期送信の初期値は、検証用の 2〜5 回/秒。これは公式の上限ではない。
- 再接続は、待ち時間（指数バックオフ）を置いてから行う。WebSocket を使うなら 1 本だけにする。
- 観測値に `session`・`seq`・`tick`・`time` を付ける。受信側は受信時刻を記録し、VM と Mac の時計が同期していると仮定しない。
- `@minecraft/server-admin` の `secrets`（`SecretString`）でトークンを送る。server-admin も server-net と同じくベータで、Beta APIs の実験が必要。足すのはアダプターのアドオンだけで、観測コアには足さない。依存の追加と実装は、この ADR を「採用」にしたあとに行う。

### 受信側（Play Conductor への提案）
Play Conductor の本体・`SECURITY.md`・ADR は、このリポジトリから参照できない。以下は、連携に必要な変更の提案で、Play Conductor の設計に合わせて取捨する。
1. 既存の汎用ローカル API は、loopback（127.0.0.1）のままにする。VM 用の受信口は、別のリスナーとして足す。
2. bind するのは、VMPal のネットワーク側の Mac のアドレス（<VMPal のローカルネットワーク> のブリッジ）だけにする。`0.0.0.0` にすると、自宅の Wi-Fi にも出てしまう。
3. 接続元は、VM のアドレス（例: <VM のローカル側のアドレス>）だけを受け付ける。ただし、アドレスは偽装できるので、これだけを頼りにしない。
4. 認証: 推測困難な共有トークン（例: 32 バイト以上の乱数）を `Authorization` ヘッダーで受け、定数時間で比較する。
   - 置き場所は、Mac 側では OS のキーチェーンなど、BDS 側では `config/<アダプターの script モジュール UUID>/secrets.json`。
   - Git・パック・ワールド・スクリプトの定数・ログには置かない。ワールドやパックの設定を、秘密の置き場所とみなさない。
   - トークンを替える手順も用意する。
5. 受け付けるのは観測のメッセージの種類だけ（`observation` など）にし、それ以外は拒否する。
6. 制限: 1 メッセージの最大サイズ（例: 16 KiB）、頻度（例: 毎秒 10 回を超えたら捨てる）、同時接続は 1 本。超えたら拒否し、ログには回数だけ残す。
7. ログに、トークンやヘッダーの値を出さない。残すのは、拒否の理由と回数だけ。
8. 受信時刻を記録し、`tick`・`time` と並べて保存する。
9. 暗号化:
   - 平文の http/ws を使うなら、同じネットワークの上で読まれうることを文書に書く。「内部ネットワークだから安全」とは説明しない。
   - TLS を使うなら、Mac 側の証明書の扱いと、server-net の `force_tls` の設定（設定場所は未確認）を決める。
10. 状態を確認する口（health）を作るなら、それにも認証を掛ける。既存の OSS（chapmanjw の MCP サーバー）は認証なしだった。

### 確かめること
- VM から Mac に届くか、Mac がどのアドレスで待ち受けるか（`docs/knowledge/bds-local-server/` §7、`docs/TESTING.md` OBS-ENV-07）。
- server-net の上限値・許可リスト・`force_tls` の設定場所（試作で確かめる）。

## 影響
- Phase 3 を採る場合のセキュリティの規則は `SECURITY.md`（外向きだけ、送り先は 1 つ、観測のメッセージだけ、トークンは server-admin の secrets、量と頻度の制限）。
- 受信側（Play Conductor）に必要な変更は、上の「受信側」。進捗は `docs/ROADMAP.md` の Phase 3。
- 採ると決めたら、この ADR を「採用」に変え、アダプターのリポジトリにも ADR を作る。採らない場合は「却下」にして理由を書く。

## 経過
- 2026-10-18: 調査の結果を受けて提案。別リポジトリに分ける案と、採否を Phase 2 の後に決める進め方が承認された（状態は保留のまま）。
- 2026-10-18: 対象を BDS だけにした（ADR-0006）。「通常ワールドで動かなくなる」は分ける理由でなくなったが、「ベータ版で、ワールドに実験的機能が必要」は残る。BDS の標準出力での回収が Phase 1 で動いた（`docs/knowledge/bds-local-server/` §8）ので、Phase 3 が必要かは Phase 2 のあとに改めて判断する。
- 2026-10-18: `docs/PLAN.md` を廃止した。そこにあった Phase 3 の規則と Play Conductor への提案（B・C）を、この ADR の「採用する場合の条件」に移した。
