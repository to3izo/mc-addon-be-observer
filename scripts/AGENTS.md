# scripts/AGENTS.md

Rules for the **TypeScript script module**. Root `AGENTS.md` still applies.

## Layout (feature-based, not Minecraft-shaped)

```
scripts/
├── main.ts                    # entry: bootstrap(features). Keep it tiny.
├── features/                  # one folder per gameplay feature / domain
│   ├── index.ts               # the registry: export const features = [...]
│   └── <feature>/
│       ├── index.ts           # exports the Feature object (id + register())
│       └── *.ts               # feature-private helpers, handlers, state
├── core/                      # engine-facing plumbing shared by all features
│   └── runtime/               # Feature contract and bootstrap (events/, commands/ as needed)
└── shared/                    # pure, dependency-free code usable anywhere
    ├── constants/addon.ts     # NAMESPACE / ADDON_SLUG — generated by pnpm init:addon
    ├── types/                 # shared TS types, ambient declarations (globals.d.ts)
    └── utils/                 # pure helpers (identifier building, math, formatting)
```

- `features/*` may import from `core/` and `shared/`, never from another feature. If two features
  need the same thing, move it to `core/` (engine-related) or `shared/` (pure).
- `core/` may import `@minecraft/*` and `shared/`, never `features/`.
- `shared/` imports nothing from `@minecraft/*` so it stays unit-testable with `node --test`.
- Imports use explicit `.ts` extensions (`./core/runtime/bootstrap.ts`). esbuild resolves them.

## Language & toolchain

- TypeScript, `strict` mode, `verbatimModuleSyntax`, `erasableSyntaxOnly` (no `enum`, no parameter
  properties, no namespaces). Use `as const` objects or union types instead of enums.
- Target is ES2022 modules; the game runs a QuickJS-based engine — no Node/DOM APIs, no `fetch`,
  no `setTimeout` (use `system.runTimeout`/`system.runInterval`), no `console.table`.
- Only `@minecraft/server` and `@minecraft/server-ui` (and other `@minecraft/*` modules that the game
  provides) may be imported at runtime. No npm runtime dependencies: everything else must be bundled
  from `scripts/`, and bundling third-party code needs an explicit instruction.
- The compiled bundle (`dist/<slug>_BP/scripts/main.js`) is **generated**. Never edit it, never commit
  it, never place `.js` files anywhere under `scripts/` or `behavior_pack/`.

## Minecraft Script API rules

1. **Version discipline.** Use only APIs available in the `@minecraft/server` version declared in
   `behavior_pack/manifest.json` (stable, non-beta). Check the installed `index.d.ts`, not memory.
   Importing a new `@minecraft/*` module requires adding it to `package.json` and to the manifest
   dependencies in the same change (`pnpm validate` enforces this).
2. **Event subscriptions** happen inside a feature's `register()`, once, at load. Store the returned
   handle if the feature can be disabled; never subscribe inside another event handler or a tick loop
   (this leaks subscriptions on every call). Prefer `afterEvents` unless you need to cancel
   (`beforeEvents`), and keep `beforeEvents` handlers minimal — many APIs are read-only there and
   mutations must be deferred with `system.run`.
3. **Ticks.** Avoid per-tick work. Use `system.runInterval(fn, n)` with the largest `n` that still
   feels right (20 = 1 s), `system.runJob` for long iterations, and event-driven logic wherever an
   event exists. Any per-tick loop must iterate only what it needs (entity queries with filters, not
   `getEntities()` on the whole dimension) and must early-return when there is nothing to do.
4. **Performance.** No allocation-heavy work in hot paths; cache dimension/objective lookups; batch
   block changes; never run commands (`runCommand`) when a typed API exists; wrap handlers in
   try/catch so a single error cannot spam the log every tick.
5. **Persistence.** Use dynamic properties (`world.setDynamicProperty`, entity properties) with
   namespaced keys `<namespace>:<key>`; keep values small and serialisable. Scoreboard objectives and
   tags are also namespaced (`<namespace>.<name>`).
6. **Identifiers** in code come from `shared/utils/identifier.ts` (`id("ruby_sword")`), never from
   hard-coded `"ns:..."` strings, so a namespace change is a one-file change.
7. **Logging.** `console.log/warn/error` only, prefixed with the feature id. No chatty logs per tick in
   shipped builds.
8. **Players and entities** can disappear between ticks: check `entity.isValid` before use, and never
   hold references across world unload.
9. **No hidden globals.** Feature state lives in the feature folder (module scope or a small class),
   not in `world`/`globalThis` properties.

## Adding a feature

1. `scripts/features/<feature>/index.ts` exporting `const <feature>Feature: Feature = { id, register }`.
2. Add it to the array in `scripts/features/index.ts`.
3. If it introduces content identifiers, define them in `behavior_pack/`/`resource_pack/` and record
   them in `docs/CONTENT.md`; add an in-game test case in `docs/TESTING.md`.
4. `pnpm validate && pnpm build`, then `pnpm deploy` and test in-game (`/reload` reloads scripts).

## Checklist before finishing

- type-check passes; no `any` without a comment explaining why
- every subscription is created once in `register()`
- no per-tick loop without a documented reason
- no `.js` added under `scripts/` or `behavior_pack/`
