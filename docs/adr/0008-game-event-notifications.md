# ADR-0008: ゲーム内の出来事を、1 行の通知と `events` メソッドで知らせる

- 状態: 採用
- 日付: 2026-10-18
- 決定者: 運営（利用者の指示）

## 背景
AI のプレイヤーが、ほかのプレイヤーの行動やゲーム内の出来事に反応できるようにしたい。たとえば、デスログ、参加・退出、チートの使用など。要求を送ったときにだけ答える仕組み（ADR-0003）では、出来事は分からない。`docs/RESEARCH.md` §2.2.1 の調査の結果は次のとおり。

- 安定版の API で取れるもの: 死亡、参加・退出・リスポーン、ディメンションの移動、ゲームモードの変更、ゲームルールの変更
- 取れないもの: チャット（メンションを含む）とコマンドの使用。`chatSend` はベータ版だけで、BDS のコンソールにも出ない

## 決定
1. 次の 7 種類を知らせる。
   - `player_join`
   - `player_leave`
   - `player_spawn`（`initialSpawn` で、初回とリスポーンを区別する）
   - `entity_die`
   - `dimension_change`
   - `game_mode_change`
   - `game_rule_change`
2. 出来事ごとに、`to3izo_bo.event {JSON}` の 1 行を出す。応答と同じく `console.log` に出し、ASCII だけにする。`session` を付け、応答とは別の連番 `seq` を付ける。
3. 最近の 64 件をメモリに保持する。新しいメソッド `events` で、`since`（連番）より後を取り直せる。取りこぼしは `missed` で分かる。
4. 1 秒に 20 件を超えた通知は捨て、捨てた数を次の通知の `dropped` に付ける。
5. `entity_die` は、プレイヤーが死んだときと、プレイヤーが倒したときだけ知らせる。
6. 変化のない `game_mode_change`（変更前と変更後が同じ）は知らせない。
7. 通知は常に出す。切り替えの設定は作らない。
8. チャットは扱わない。AI の操作ツールが、画面から読む。

## 理由・検討した案
- **行で知らせる（押し出し）**: BDS の標準出力を読んでいるツールなら、遅れなく受け取れる。要求の経路（ADR-0003）と同じ読み方で済む。
- **`events` メソッド（取り直し）**: ツールが行を読み落としたり、起動が遅れたりしても、追いつけるようにした。保持するのはメモリだけで、ワールドには書かない（読み取り専用を保つ）。`/reload` で消えることは、`session` が変わることで分かる。
- **死亡の範囲を絞った**: すべてのモブの死亡を知らせると、トラップや戦闘でログが埋まる。AI のプレイヤーに関係する死亡（プレイヤーの死亡、プレイヤーによる討伐）に限った。
- **切り替えの設定を作らなかった**: 設定を保存するにはワールドに書く必要がある（dynamic property など）。種類を絞って量を抑え、常に出すことにした。
- **チャットを扱わなかった**: ベータ版の `chatSend` を観測コアで使うと、ADR-0001 に反し、ワールドに実験的機能が要る。必要になったら、ADR-0004 のアダプターと同じく、別のパックで扱う。

## 影響
- `docs/PROTOCOL.md`（§5.9 `events`、§10 通知の行）
- `capabilities`（`events`・`transport.eventPrefix`・`limits`）
- `docs/TESTING.md`（U-EVT、OBS-EVT）
- `SECURITY.md`（通知にもプレイヤー名と位置が入る）

## 経過
- 2026-10-18: 利用者の指示で実装し、BDS 1.26.52.3 で 7 種類すべてを確認した。
- 2026-10-18: 試験の途中で、BDS が参加のときに `Creative → Creative` の `game_mode_change` を 2 回出すと分かった（`force-gamemode=true` のため）。変化のないものは知らせないことにした（決定 6）。
- 2026-10-18: 追加のイベント 8 種類を、要求で付け外しできるように足した（ADR-0014）。状態はメモリだけに持つ。決定 7 は、ここの 7 種類に限って残る。
